10 · 实战：自动测试 + 自动部署

预计用时：60-75 分钟（选一条路线走通即可） · 前置：第 9 课 · 速查表：Actions 速查表

本课目标 搭一条真正的流水线：push → 自动构建/测试 → 自动部署上线。完成后你的项目实现全自动发布。
开工前告诉我 你的项目是什么类型？（静态网页 / Node.js / Python / 其他）下面有对应路线，选一条走即可。

1. 路线 A：静态网站 / 文档 → GitHub Pages（最简单，强烈推荐先走通）

GitHub Pages 免费托管静态站点。整条路线就 4 步：建 workflow 文件 → 设 Pages 源 → 看机器人干活 → 打开网页验收。下面逐步带你做。

Step 1 · 创建 workflow 文件（路径是固定的，别写错）

Actions 只认仓库根目录下 .github/workflows/ 里的 yml 文件——这两个文件夹名和位置是硬规定，文件名倒可以随便取（惯例叫 deploy.yml）。

最省事的方式是直接在 GitHub 网页上建，不用碰本地项目：

  1. 打开仓库主页 → 文件列表上方 Add file → Create new file
  2. 在文件名输入框里输入完整路径：.github/workflows/deploy.yml（输入斜杠时会自动创建文件夹）
  3. 粘贴下面的内容，右上角 Commit changes 提交——网页上 commit 就等于 push，提交那一瞬间 workflow 已经被触发
name: 构建并部署到 Pages
on:
  push:
    branches: [main]

jobs:
  deploy:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      pages: write
      id-token: write
    steps:
      - uses: actions/checkout@v4
      # 如果是纯 HTML 项目，跳过构建，直接发布整个目录：
      - uses: actions/upload-pages-artifact@v3
        with:
          path: .          # 有构建产物就写 dist/ 或 build/
      - uses: actions/deploy-pages@v4
path 写什么？ 问自己一个问题：浏览器直接打开哪个文件夹里的 index.html 能看到你的网站，path 就写哪个。纯 HTML 且 index.html 在仓库根目录 → path: .；React/Vue 项目 → 先加构建步骤（npm ci && npm run build），path 写 dist/ 或 build/。

Step 2 · 把 Pages 源设为 GitHub Actions（必做，漏了必报错）

  1. 仓库主页 → 顶部 Settings 标签（需要仓库管理员权限）
  2. 左侧边栏 Code and automation 分组下点 Pages
  3. 在 Build and deployment 下，把 Source 下拉框从 "Deploy from a branch" 改成 GitHub Actions（选完自动保存，没有保存按钮）

Step 3 · 看机器人干活

回到仓库主页 → 顶部 Actions 标签 → 点最新那次运行 → 等所有步骤变绿。两个验收点：

  • 展开最后一步的日志，里面会直接打印部署完成的 URL：https://你的用户名.github.io/仓库名/
  • 仓库主页右侧边栏会出现 Deployments 记录

Step 4 · 验收上线

浏览器打开 https://你的用户名.github.io/仓库名/（首次部署后要等 1-2 分钟才能打开）。看到页面那一刻，你就完成了从本地到全自动上线的闭环 🎉

路线 A 常见故障

现象原因解决
Actions 里报错 "Pages not yet set up"Step 2 没做，Source 还不是 GitHub Actions回去把 Source 改成 GitHub Actions，重跑 workflow
Actions 标签里空空如也yml 没放在 .github/workflows/ 下，或文件名后缀不是 .yml/.yaml，或没提交到 main检查路径、后缀和分支名
全绿但打开是 404path 指错了，产物里没有 index.html确认 index.html 在哪个目录，path 就写那里
页面能开但样式/图片全挂站点在 /仓库名/ 子路径下，资源用了绝对路径资源改用相对路径；框架站去查该框架的 base path 配置

2. 路线 B：Node.js 项目 → 自动安装依赖 + 测试

开工前自检（一半的失败都省在这里）
  • 先在本地终端跑 npm test，确认是绿的——CI 只是在一台干净机器上重跑你的命令，本地红它必红
  • package-lock.json 必须存在且已提交——npm ci 靠它安装，没有它第一步就报错
  • 项目没有测试？把 npm test 换成 npm run build，先验证能构建也算 CI

建文件的方式和路线 A 的 Step 1 完全一样：网页上 Add file → Create new file，路径输 .github/workflows/ci.yml，粘贴下面内容，Commit。然后去 Actions 标签看变绿。

name: CI
on: [push]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20      # 改成和你本地一致：终端跑 node -v 看版本号
          cache: npm            # 缓存依赖，下次跑得快（依赖 package-lock.json）
      - run: npm ci
      - run: npm test
现象原因解决
npm ci error ENOENT package-lock.json锁文件没提交到仓库本地 npm install 生成后 commit + push
本地能过，CI 红Node 版本不一致，或本地有残留环境变量/全局包把 node-version 改成和你本地一致；看 CI 日志里具体哪步红的
测试需要数据库/API key 才能跑测试依赖外部服务暂时超出本课范围，把报错贴给我单独设计

3. 路线 C：Python 项目

开工前自检
  • 有 requirements.txt 吗？没有就在项目目录里生成：pip freeze > requirements.txt（最好在你的虚拟环境里生成，列表才准），然后 commit + push
  • 有测试文件吗？pytest 找不到任何测试会以退出码 5 结束——CI 会红。没有测试就先把那行换成 run: python -m compileall .（验证所有文件能编译）或冒烟跑一下主程序

同样在网页上建 .github/workflows/ci.yml：

name: CI
on: [push]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"   # 改成和你本地一致：python --version 看版本
      - run: pip install -r requirements.txt
      - run: pytest                # 没测试就先换成 python -m compileall .
现象原因解决
ModuleNotFoundError: No module named 'xxx'那个包没写进 requirements.txtpip freeze > requirements.txt 重新生成后 push
pytest 显示 exit code 5 / no tests ran项目里没有测试文件写个最小测试，或换 compileall 冒烟检查
本地能跑 CI 红Python 版本不一致python-version 改成和本地一致

4. Secrets：密码不要写在 yml 里

部署要用的密钥（服务器密码、API key、token）不能写进 yml——公开仓库里任何人都看得到，而且 git 历史里永远抹不掉。正确做法分两步：

第一步：把密钥存进 GitHub

  1. 仓库 Settings → 左侧 Secrets and variables → Actions
  2. 右上角 New repository secret
  3. Name 填 DEPLOY_TOKEN（名字全大写+下划线，引用时大小写必须一致），Secret 粘贴值 → Add secret

存进去后就看不见了（只能覆盖或删），这是设计如此，不是 bug。

第二步：在 yml 里引用

- name: 部署
  run: echo "token 是 $DEPLOY_TOKEN"
  env:
    DEPLOY_TOKEN: ${{ secrets.DEPLOY_TOKEN }}

跑一次去日志里看：那行会显示 token 是 ***——GitHub 自动把密钥打码，这就是它在保护你。

有自己的服务器？ 服务器部署的常见做法：Actions 通过 SSH 登录你的服务器执行 git pull && 重启服务（用 appleboy/ssh-action + SSH secret）。有这个需求告诉我，我给你出定制版任务。

5. 加分项：打 tag 自动发 Release

回忆第 8 课手动发 Release 的活儿，交给机器人。在仓库里新建 .github/workflows/release.yml：

name: 发 Release
on:
  push:
    tags: ["v*"]        # 只在推 v 开头的 tag 时触发

jobs:
  release:
    runs-on: ubuntu-latest
    permissions:
      contents: write   # 创建 Release 需要写权限，不写会报 403
    steps:
      - uses: actions/checkout@v4
      - uses: softprops/action-gh-release@v2   # 自动创建 Release

然后在本地终端：

git tag v0.2.0
git push origin v0.2.0     # 注意：tag 不会随普通 push 自动上传，要单独推

去仓库主页左侧 Releases 看效果——从此发布 = 两条命令，测试、发布全部自动。

6. 动手任务

  1. 按你的项目路线（A/B/C）在网页上创建 .github/workflows/ 下的 workflow 文件，push，去 Actions 标签看到绿色对号。
  2. 路线 A：打开你的 username.github.io/仓库名 页面截图🎉 / 路线 B、C：故意写坏一个测试让它变红，看一次红色长什么样（知道失败长什么样才会看日志），再修绿。
  3. 加一个 secret（起名叫 DEMO_SECRET，值写今天的日期），在某个 step 里用 env + echo 引用它——去日志里确认它显示为 *** 而不是明文（这正是它在保护你）。
  4. （可选）按第 5 节建好 release.yml，本地打 v0.2.0 并单独推 tag，去 Releases 页看自动发布的效果。

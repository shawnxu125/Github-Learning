04 · 正面解决合并冲突

预计用时：40 分钟 · 前置：第 3 课 · 速查表：分支速查表

本课目标 亲手故意制造一次冲突，然后按固定流程解决它。从此看到 CONFLICT 不再心慌——它只是 Git 在问："这一行你想听谁的？"

1. 冲突什么时候发生

只有一种情况：两条分支改了同一个文件的同一区域，然后你 merge。Git 无法替你决定保留谁的版本，于是停下来问你。

冲突不是错误，不需要"修复"仓库。它只是一个待回答的问题。

2. 冲突长什么样

merge 冲突后，文件里会出现这样的标记：

<<<<<<< HEAD
main 分支上这一行的写法
=======
feature 分支上这一行的写法
>>>>>>> feature-login

读法：<<<<<<< HEAD 到 ======= 之间是你现在所在分支的版本；======= 到 >>>>>>> 之间是被合并分支的版本。

3. 解决冲突的标准三步

  1. 编辑文件：删掉三行 <<<<<<< / ======= / >>>>>>> 标记，留下你想要的最终内容（可以选一边，也可以两段都留，或重写成全新的）。
  2. git add 该文件——add 在这里的含义是"我裁决完了"。
  3. git commit（不用 -m 也行，Git 自动写合并信息）——合并完成。
VSCode 外挂 VSCode 会在冲突文件里显示 Accept Current / Accept Incoming / Accept Both 按钮，点一下自动清理标记。图形界面和命令行此时完美协作——这正是你保留 VSCode 的理由。
逃生门 冲突太多想整个放弃？git merge --abort 一键回到 merge 之前的状态，毫发无损。任何时候都可以先 abort 再重新来。

4. 动手任务：故意制造冲突

  1. 在 main 上把 notes.md 第一行改成 main 的版本，commit。
  2. git switch -c feature-conflict，把同一行改成 feature 的版本，commit。
  3. git switch main，git merge feature-conflict——恭喜，CONFLICT！🎉
  4. 用 VSCode 打开文件，观察冲突标记和 Accept 按钮；裁决后 add + commit。
  5. 再来一遍，但这次在冲突状态下运行 git merge --abort，感受一键逃生。
  6. 收尾：git branch -D feature-conflict，push。
